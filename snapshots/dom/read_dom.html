Satu Server, Satu Tumpukan

Server Single-Tier Stack artinya web server, runtime aplikasi, dan database semua berjalan di satu mesin yang sama.

Bayangkan sebuah warung makan yang memiliki dapur, meja makan, dan tempat penyimpanan piring dalam satu lokasi. Pelanggan memesan makanan, Ibu koki memasaknya, lalu makanan disajikan kepada pelanggan. Semua aktivitas berlangsung di tempat yang sama.

Konsep ini bisa dimiripkan dengan yang kita bahas yaitu Single-Tier Stack, ketika komponen utama aplikasi, seperti web server, runtime aplikasi, dan database, dimasak lalu disajikan ke kita sebagai makanan atau halaman.

Lalu, bagaimana prosesnya ketika pengunjung membuka website yang menggunakan Single-Tier Stack?

Dari diagram warung makan di atas, terlihat bahwa semua proses terjadi di satu lokasi yang sama. Di balik sajian makanan yang tampak sederhana, sebenarnya ada serangkaian peran, aturan, dan alat yang bekerja bersama agar pesanan bisa diproses dan diantar kembali dengan tepat.

Hal inilah yang juga terjadi pada server single-tier stack. Ketika browser mengirim permintaan, ada komponen-komponen yang bertugas menerimanya, memproses logika aplikasi, mengambil data jika dibutuhkan, lalu mengembalikan hasilnya ke pengguna.

Kebutuhannya menyesuaikan tujuan aplikasi, pengalaman yang ingin diberikan kepada pengguna, kebutuhan keamanan, serta lingkungan deployment. Ada yang bisa bersifat hampir wajib (misalnya HTTPS untuk situs publik), ada pula yang hanya ditambahkan saat benar-benar dibutuhkan (misalnya cache untuk meningkatkan performa).

Kombinasi stack ini seperti bahan makanan dasar yang digunakan oleh warung tersebut. Dalam konteks teknologi seperti sistem operasi, web server, bahasa pemrograman, framework, dan database, membentuk sebuah variasi yang disebut solution stack.

Setiap stack memiliki susunan teknologi dan tujuan yang berbeda sesuai kebutuhan aplikasi.

Beberapa contoh technology stack beserta komponen dan kegunaannya.

1. JavaScript & TypeScript Stack

Stack yang menggunakan JavaScript atau TypeScript untuk membangun antarmuka pengguna (frontend) dan logika server (backend). Dengan Node.js, Bun, atau Deno, JavaScript dapat dijalankan di sisi server sehingga satu bahasa dapat mencakup seluruh tumpukan aplikasi.

Stack Komponen utama Keterangan
MEAN MongoDB, Express.js, Angular, Node.js Menggunakan Angular untuk frontend SPA, Express.js sebagai backend framework, Node.js sebagai runtime server, dan MongoDB sebagai database NoSQL. Cocok untuk aplikasi enterprise yang membutuhkan struktur kuat dan TypeScript support bawaan melalui Angular.
MERN MongoDB, Express.js, React, Node.js Menggunakan React untuk frontend berbasis komponen, Express.js untuk API backend, Node.js untuk runtime, dan MongoDB sebagai database. Sangat populer untuk aplikasi web modern dan mobile backend karena fleksibilitas React dan ekosistem npm yang luas.
MEVN MongoDB, Express.js, Vue.js, Node.js Menggunakan Vue.js sebagai frontend framework progresif, Express.js untuk backend, Node.js untuk runtime, dan MongoDB untuk database. Dikenal ringan, mudah dipelajari, dan cocok untuk aplikasi skala menengah yang membutuhkan reactivity yang cepat.
PERN PostgreSQL, Express.js, React, Node.js Mengganti MongoDB dengan PostgreSQL sebagai database relasional (ACID compliant), sambil tetap menggunakan React, Express.js, dan Node.js. Ideal untuk aplikasi yang membutuhkan integritas data, query kompleks, dan relasi antar tabel yang ketat.
Next.js Stack Next.js, React, Node.js, PostgreSQL atau MySQL Framework React yang mendukung Server-Side Rendering (SSR), Static Site Generation (SSG), dan API routes dalam satu proyek. Cocok untuk aplikasi yang membutuhkan SEO baik, performa muat halaman cepat, dan full-stack dalam satu repository.
T3 Stack TypeScript, Tailwind CSS, tRPC, Next.js, Prisma, PostgreSQL Stack full-stack TypeScript yang menegaskan type safety dari database sampai frontend. tRPC menghilangkan perlu REST API manual, Prisma sebagai ORM type-safe, dan Tailwind untuk styling. Sangat cocok untuk tim yang mengutamakan keamanan tipe dan pengembangan cepat.
JAMstack JavaScript, API, Markup Pendekatan arsitektur yang memisahkan frontend markup dari backend. JavaScript dijalankan di sisi klien, data diambil melalui API, dan markup difoto statis pada waktu build. Cocok untuk situs konten, e-commerce statis, dan aplikasi yang memerlukan keamanan serta skalabilitas tinggi tanpa server konvensional.
Bun Stack Bun, Elysia atau Hono, SQLite atau PostgreSQL, React atau Vue Menggunakan Bun sebagai runtime JavaScript yang menggantikan Node.js dengan startup lebih cepat dan penggunaan memori lebih hemat. Elysia atau Hono sebagai web framework yang ringan, dan database relasional untuk penyimpanan data. Cocok untuk microservices, serverless, dan aplikasi yang sensitif terhadap latensi serta resource. Perlu diperhatikan ekosistemnya masih lebih muda dibanding Node.js.

2. PHP Stack

Stack yang berpusat pada bahasa PHP untuk pengembangan web, biasanya dijalankan di sisi server dengan web server dan database relasional.

Stack Komponen utama Keterangan
Laravel PHP, Laravel, MySQL atau PostgreSQL, Nginx atau Apache Framework PHP modern yang menyediakan fitur lengkap seperti routing, autentikasi, Eloquent ORM, dan blade templating. Cocok untuk aplikasi web skala kecil hingga besar dengan pengembangan yang terstruktur dan dokumentasi yang luas.
Symfony PHP, Symfony, berbagai database, Nginx atau Apache Komponen modular dan reusable untuk aplikasi PHP enterprise. Digunakan sebagai fondasi banyak framework lain termasuk Laravel. Sangat fleksibel untuk aplikasi skala besar yang membutuhkan kontrol penuh atas arsitektur.
LAMP Linux, Apache, MySQL atau MariaDB, PHP Stack klasik dan paling terkenal untuk aplikasi web dinamis. Linux sebagai sistem operasi, Apache sebagai web server, MySQL/MariaDB sebagai database, dan PHP sebagai bahasa pemrograman. Mudah dihosting dan banyak didukung penyedia hosting.
LEMP Linux, Nginx, MySQL atau MariaDB, PHP Variasi LAMP yang mengganti Apache dengan Nginx. Nginx lebih efisien dalam menangani koneksi bersamaan dan konten statis, sehingga cocok untuk aplikasi dengan trafik tinggi atau yang membutuhkan performa web server lebih baik.
WAMP Windows, Apache, MySQL atau MariaDB, PHP Stack berbasis Windows untuk pengembangan dan hosting aplikasi web PHP. Cocok untuk lingkungan yang sudah menggunakan infrastruktur Microsoft dan memerlukan kompatibilitas dengan aplikasi Windows.
WIMP Windows, IIS, MySQL atau MariaDB, PHP Stack berbasis Windows yang menggunakan IIS (Internet Information Services) sebagai web server menggantikan Apache. Cocok untuk organisasi yang sudah terintegrasi dengan ekosistem Microsoft dan ingin menjalankan PHP di atas Windows Server.
FAMP FreeBSD, Apache, MySQL atau MariaDB, PHP Variasi LAMP yang menggunakan FreeBSD sebagai sistem operasi. Dikenal stabil, aman, dan efisien untuk networking serta networking stack. Cocok untuk server yang memprioritaskan stabilitas sistem operasi berbasis BSD.
XAMPP Lintas platform, Apache, MariaDB atau MySQL, PHP, Perl Paket pengembangan web all-in-one yang mudah diinstal di Windows, Linux, dan macOS. Digunakan terutama untuk pembelajaran dan prototipe lokal sebelum deploy ke server produksi.

3. Python Stack

Stack yang menggunakan bahasa Python untuk pengembangan web, dari mikro framework hingga full-stack framework dengan banyak fitur bawaan.

Stack Komponen utama Keterangan
Python-Django Python, Django, PostgreSQL atau MySQL, Nginx atau Apache, Gunicorn Framework "batteries included" yang menyediakan admin panel, autentikasi, ORM, dan fitur keamanan bawaan. Cocok untuk aplikasi web skala besar yang membutuhkan pengembangan cepat dengan standar keamanan yang tinggi.
FastAPI Python, FastAPI, PostgreSQL atau MySQL, Nginx, Uvicorn Framework modern untuk membangun API dengan validasi data otomatis menggunakan Pydantic dan dokumentasi Swagger/OpenAPI. Tinggi performa karena asynchronous dan cocok untuk microservices serta machine learning API.
Flask Python, Flask, berbagai database, Nginx atau Apache, Gunicorn Micro framework yang ringan dan fleksibel. Memberikan kontrol penuh kepada pengembang tanpa memaksa struktur tertentu. Cocok untuk aplikasi kecil, prototipe, atau layanan yang membutuhkan kustomisasi maksimal.
Pyramid Python, Pyramid, berbagai database Framework fleksibel yang dapat digunakan untuk aplikasi kecil hingga besar. Memungkinkan pengembang memilih komponen sesuai kebutuhan dan cocok untuk aplikasi yang perlu berkembang secara bertahap.

Memilih Platform untuk Menjalankan Stack

Setelah memilih technology stack yang akan digunakan, langkah berikutnya adalah menentukan platform tempat stack tersebut dijalankan. Pilihannya beragam, mulai dari server fisik (bare metal), virtual machine (VM), container, hingga layanan cloud seperti PaaS dan serverless.

Dalam dunia server, pilihan ini menentukan bagaimana aplikasi dijalankan, sumber daya komputasi disediakan, dan infrastruktur dikelola. Referensi: Wikipedia — Computing platform.

Bayangkan kamu sudah punya resep, bahan, dan peralatan untuk membuka warung makan. Sekarang, kamu perlu menentukan tempat untuk menjalankan usaha tersebut. Kamu bisa membangun warung sendiri, menyewa tempat, berbagi fasilitas dengan pedagang lain, atau membuka gerai sementara sesuai kebutuhan.

PaaS (Platform as a Service) Buka warung franchise siap pakai. Bawa resep saja, toko dan listrik sudah disediakan. Platform yang menangani infrastruktur, kamu hanya mengunggah kode. Heroku, Render, Railway

Perbedaan Penting

  • VMware Workstation dan Fusion = virtualisasi untuk komputer pribadi (lokal), cocok buat belajar di rumah.
  • VMware ESXi / vSphere dan Proxmox VE = virtualisasi untuk server produksi, cocok buat kelola banyak VM sekaligus.
  • Bare Metal merujuk pada sistem yang berjalan langsung di hardware fisik. Dedicated Server merujuk pada server fisik yang disewa khusus untuk satu pelanggan. Keduanya sering berkaitan, tapi bukan hal yang sama.

Hubungannya dengan Single-Tier Stack

Single-tier berarti semua komponen stack (web server, runtime aplikasi, dan database) berada di satu tempat yang sama — misalnya dalam satu VM, satu container, atau satu server fisik.

Single-tier tidak berarti harus menggunakan VM atau container. Stack ini juga bisa berjalan langsung di bare metal, dedicated server, atau bahkan di Platform as a Service (PaaS), asalkan seluruh komponennya tetap berada dalam satu platform yang sama.

Penting untuk membedakan:

  • Platform (tempat pelaksanaan) = fasilitas tempat stack dijalankan (bare metal, VM, container, PaaS, serverless, dll.).
  • Arsitektur tier = cara pembagian komponen aplikasi (single-tier, multi-tier, dll.).

Pilihan platform ini akan sangat memengaruhi biaya operasional, fleksibilitas, skalabilitas, keamanan, dan cara aplikasi dipelihara. Tidak ada satu pilihan yang selalu paling baik — semuanya bergantung pada kebutuhan proyek.

Tips Buat Mulai

  1. Pahami alur aplikasi
    Pelajari bagaimana HTTP request dikirim dari browser ke web server, diproses oleh aplikasi, berinteraksi dengan database jika diperlukan, lalu kembali sebagai HTTP response ke browser. Cobalah menjalankan aplikasi sederhana dan amati kode status seperti 200 OK, 404 Not Found, dan 500 Internal Server Error untuk membedakan permintaan yang berhasil dan gagal.
    Referensi: MDN — How the Web Works

  2. Pilih technology stack sesuai kebutuhan
    Pilih stack berdasarkan kebutuhan aplikasi, kemampuan tim, ketersediaan dokumentasi, keamanan, performa, dan biaya. Untuk mulai belajar, gunakan stack yang relatif sederhana, seperti LAMP atau LEMP untuk PHP, maupun MERN untuk JavaScript. Pelajari fungsi setiap komponen terlebih dahulu sebelum menambahkan teknologi lain.

  3. Mulai dengan lingkungan lokal
    Sebelum menerapkan ke server publik, bangun dan jalankan stack-mu di komputer sendiri menggunakan instalasi lokal, VirtualBox untuk virtual machine (VM), atau Docker untuk container. Cobalah menjalankan, menghentikan, dan menjalankan ulang aplikasi untuk memahami konfigurasi, dependensi, serta kebutuhan sumber dayanya.
    Perhatikan perbedaan: VM memiliki sistem operasi tamu sendiri, sedangkan container berbagi kernel host.
    Referensi: Docker — What is a Container?

  4. Uji aplikasi setelah dijalankan
    Aplikasi yang berhasil dinyalakan belum tentu berfungsi dengan benar. Coba akses melalui browser, periksa respons HTTP, pastikan aplikasi dapat memproses permintaan, dan uji operasi baca-tulis ke database jika digunakan.
    Untuk melatih kemampuan troubleshooting, hentikan salah satu komponen di lingkungan uji, amati dampaknya, periksa log, lalu jalankan kembali komponen tersebut dan pastikan aplikasi pulih dengan normal.
    Referensi: Docker — Run Your First Container

  5. Pahami HTTP dan HTTPS sebelum menerapkan TLS
    Mulailah dengan mempelajari perbedaan HTTP dan HTTPS. Di lingkungan pengujian, coba akses aplikasi melalui HTTP, lalu aktifkan HTTPS menggunakan sertifikat uji. Amati perbedaan protokol, validasi sertifikat, serta peringatan yang muncul di browser saat sertifikat tidak dipercaya atau tidak valid.
    Setelah memahaminya, terapkan HTTPS dengan sertifikat yang valid sebelum membuka website ke publik. TLS melindungi jalur komunikasi melalui enkripsi, autentikasi server, dan integritas data, namun tidak otomatis mengamankan kode aplikasi, autentikasi, atau database.
    Referensi: OWASP — Transport Layer Security Cheat Sheet

  6. Pantau performa sebelum melakukan optimasi
    Catat penggunaan CPU, RAM, ruang disk, waktu respons, dan log saat aplikasi berjalan dalam kondisi normal. Lakukan pengujian beban secara bertahap dan bandingkan hasilnya untuk melihat di mana bottleneck mulai muncul.
    Jika ditemukan masalah, ubah satu hal pada satu waktu, ukur kembali hasilnya, dan baru pertimbangkan menambah cache atau sumber daya.
    Referensi: Prometheus — Overview

  7. Uji cache dan pemulihan backup
    Jika aplikasi sering membaca data yang sama, bandingkan waktu respons dan beban database sebelum dan sesudah menggunakan cache. Perhatikan juga konsistensi datanya saat data asli berubah.
    Untuk data penting, buat backup database dan file aplikasi, lalu coba pulihkan ke lingkungan pengujian. Pastikan data hasil pemulihan benar-benar dapat dibaca dan digunakan kembali. Keberhasilan membuat backup saja belum membuktikan pemulihan berhasil.
    Referensi: PostgreSQL — Backup and Restore

  8. Dokumentasikan konfigurasi dan perubahan
    Catat versi perangkat lunak, dependensi, konfigurasi penting, serta langkah untuk menjalankan aplikasi. Gunakan Git untuk melacak perubahan kode agar mudah ditelusuri atau dikembalikan jika dibutuhkan.
    Sebagai latihan, coba bangun ulang lingkungan hanya berdasarkan dokumentasi yang kamu buat. Jika bisa diulang tanpa bergantung pada ingatan, artinya dokumentasimu sudah cukup jelas.
    Referensi: Pro Git — About Version Control

  9. Kenali batas single-tier
    Pada arsitektur single-tier, web server, runtime aplikasi, dan database berjalan pada satu mesin yang sama. Gangguan pada mesin ini bisa berdampak pada seluruh aplikasi.
    Cobalah hentikan salah satu komponen di lingkungan pengujian untuk melihat risikonya, atau simulasikan kehabisan sumber daya dan mesin yang tidak dapat diakses.
    Jika kebutuhan aplikasi meningkat, evaluasi opsi seperti optimasi, penambahan kapasitas, redundansi, atau pemisahan komponen ke mesin dan layanan berbeda berdasarkan masalah yang terukur, kebutuhan ketersediaan, dan biaya operasional.
    Referensi: Red Hat — What Is High Availability?

Rumus Memilih Stack dan Deployment Environment

  • Untuk belajar: minat pribadi + kemudahan penggunaan + dokumentasi + ketersediaan materi belajar.
  • Untuk proyek baru: kebutuhan aplikasi + jumlah dan pola pengguna + kompetensi tim + keamanan + hasil uji performa + biaya operasional.
  • Untuk migrasi stack atau deployment: masalah sistem lama + manfaat migrasi yang terukur + biaya dan risiko migrasi + kompatibilitas + dampak terhadap pengguna + dukungan jangka panjang.

Intinya: Pilih stack dan deployment environment berdasarkan kebutuhan aplikasi, skala pengguna, kemampuan tim, dan hasil pengujian. Untuk memahami keputusan teknis di dunia nyata, pelajari studi kasus engineering dari perusahaan yang menghadapi tantangan serupa.

Kesimpulan

Server Single-Tier Stack adalah arsitektur di mana komponen utama aplikasi, yaitu web server, runtime aplikasi, dan database, berjalan pada satu mesin yang sama.

Prosesnya mirip dengan warung makan satu lokasi: browser mengirim HTTP Request ke server, aplikasi memproses permintaan tersebut (serta mengakses database jika dibutuhkan), lalu mengembalikannya dalam bentuk HTTP Response ke pengguna.

Dengan membedakan komponen inti (OS, web server, runtime aplikasi, dan database) dan komponen pelengkap (web client, TLS & sertifikat TLS, serta cache), kita bisa lebih mudah mengenali mana yang wajib agar aplikasi bisa berjalan, dan mana yang bisa ditambahkan untuk meningkatkan keamanan, performa, maupun kenyamanan pengguna.

Terdapat beragam technology stack seperti LAMP, MERN, Django, Spring Boot, dan lainnya yang bisa dipilih sesuai kebutuhan. Stack ini juga bisa dijalankan di berbagai platform, mulai dari bare metal, VM, container, PaaS, hingga serverless.

Meski sederhana, mudah dipelajari, dikonfigurasi, dan diuji, arsitektur ini memiliki keterbatasan sumber daya dan berpotensi menjadi Single Point of Failure (SPOF) karena seluruh komponen bergantung pada satu mesin yang sama.

Intinya: Mulailah dari arsitektur single-tier untuk membangun pemahaman dasar tentang cara kerja server. Pilih stack dan platform yang sesuai kebutuhan, terapkan praktik keamanan sejak awal, lakukan pengujian dan dokumentasi dengan baik. Jika aplikasi berkembang dan membutuhkan skalabilitas serta ketersediaan yang lebih tinggi, barulah pertimbangkan untuk beralih ke arsitektur multi-tier.
